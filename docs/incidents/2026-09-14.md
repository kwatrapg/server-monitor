# Incident — 2026-09-14: Servers page DataTables "Ajax error"

**Reported:** Clicking **Servers** showed a DataTables `Ajax error` (datatables.net/tn/7)
and the list failed to load. Searching by name afterwards did list servers.

**Environment:** production, `sahil@172.105.19.14:/var/www/html/desc-new`
(`https://descriptive.24x7up.com/?route=servers`).

## Root cause

`Server::quickStats()` (`includes/classes/class.server.php`) threw an uncaught PHP
fatal while computing disk/RAM stats for one specific server whose latest
`app_servers_history` row fails to `gzuncompress()` (corrupt/truncated data at the
source — that server's agent/history, not the fix below). This ran inside the loop
in `includes/controllers/json.php` (`case "servers"`) that builds the ajax response
for the **unfiltered** list, so the whole response died (empty body / 500) and
DataTables reported an ajax error.

Searching by name excluded that one server from the result set, so the crash never
ran and the search "worked" — which is why the failure looked filter-dependent.

Two PHP-8 strictness issues compounded, in order:
1. `DivisionByZeroError` — `$diskused / $disktotal` with `$disktotal == 0` (empty
   disk list from the unusable data). The file already guards the equivalent CPU
   calc (`if($realtotal == 0) $realtotal = 0.01;`) but the disk calc had no such
   guard, in both the `linux` and `windows` branches of `quickStats()`.
2. `TypeError: Unsupported operand types: string + string` — once (1) was fixed,
   `Server::extractData()` returning `""` for a missing/corrupt tag hit PHP 8's
   stricter arithmetic (`"" + ""` throws in PHP 8; PHP 7 silently coerced to `0`).

A secondary finding during diagnosis: `index.php` set `error_reporting(0)` in
production, which (in addition to suppressing display) also suppresses **logging**
of runtime fatals — so this class of bug previously left no trace in any log,
anywhere, which is why it took live debugging (with temporary, non-displaying log
access) to catch it.

## Fix

Applied to both production and this repo (`includes/classes/class.server.php`,
`index.php`):

- Guard `$disktotal == 0` before the division, in both platform branches of
  `quickStats()` — same pattern as the existing CPU guard.
- Cast the RAM figures pulled via `extractData()` to `(float)` before arithmetic,
  so a missing/corrupt tag degrades to `0` instead of throwing.
- `error_reporting(E_ALL)` with `display_errors` still **off** in production —
  restores fatal-error logging (via the existing `log_errors`/`error_log` PHP-FPM
  pool config) without exposing anything to visitors.

## Verified

- Reproduced the exact fatal via the (log-only) diagnostic patch and
  `/var/log/php-fpm/www-error.log`:
  `Uncaught DivisionByZeroError ... class.server.php:331`, then after fix 1,
  `Uncaught TypeError: Unsupported operand types: string + string ... class.server.php:339`.
- After both fixes: Servers page reloads cleanly, confirmed by the reporter. Only
  non-fatal warnings remain for the one server with corrupt history data (it shows
  blank/0 load stats instead of crashing the page).

## Not fixed by this change (follow-up)

- The corrupt `app_servers_history` row itself — that server's agent/history should
  be checked; its most recent stats will show as blank/0 until it reports fresh,
  valid data.
- `config.php` on production has hand-edited fallback DB credentials/name (`dnew`/
  `desc`/`S3cR3t`) that don't match this repo's tracked defaults, and `.env` on
  that host does not set `DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST` at all —
  confirmed intentional (database migration), but worth reconciling `.env` on that
  host so credentials aren't only living in a hand-edited `config.php`.
- Investigation opened separately: server detail/graph pages showing stale (not
  fresh) data across time-range checks and server switches — see the next
  section, now fixed in this same incident.

# Incident 2 — 2026-09-14: Server/website/check "manage" pages show stale time-range data

**Reported:** After picking a time range (e.g. "Last 30 Minutes", "Last 60
Minutes") on a server's manage page, checking another server or re-checking the
same server later kept showing an old/stale window instead of current data.

## Root cause

Two separate bugs, both in the manual date-range picker path (the default
"auto" 3-hour view was never affected — it already recomputes every load):

1. **Route-name mismatch disabling the reset-on-switch logic.**
   `includes/controllers/data.php` resets the saved range when you switch
   assets, but compared the route to the literal string `"servers/manage"`.
   The real route for a server's page is `"servers/manage-linux"` or
   `"servers/manage-windows"` (split by OS — see `template/header.php`), so
   that comparison could never match and the reset never fired for server
   pages. The identical typo was also in the `$autorefresh_pages` list,
   silently disabling the auto-refresh countdown on server pages only
   (websites/checks/domains/ssl use a single `manage` route each and were
   unaffected).
2. **Presets stored as a frozen absolute snapshot, not a sliding window.**
   Picking "Last 30 Minutes" computed `now - 30m` and `now` once, client-side,
   and stored those exact timestamps in `$_SESSION['range_start']`/`['range_end']`
   (`includes/classes/class.app.php` `setRange()`). Once `range_type` became
   `"manual"`, nothing ever recomputed that window relative to a later "now" —
   unlike the "auto" 3-hour view, which `includes/loader.php` already
   recomputes on every single request.

## Fix

Applied to both production and this repo:

- `includes/controllers/data.php` — route checks now match
  `servers/manage-linux` / `servers/manage-windows` (both the reset-on-switch
  block and `$autorefresh_pages`).
- `template/footer.php` — the date-range picker JS now also sends how many
  seconds wide the chosen window is (`range_offset`) whenever the click was a
  named preset (looked up against the same `ranges` object the picker itself
  uses); a genuine custom/calendar-picked range still sends no offset and
  stays a fixed, absolute window as picked.
- `template/pages/servers/manage-{linux,windows}.php`,
  `template/pages/checks/manage.php`, `template/pages/websites/manage.php` —
  added the `range_offset` hidden field to `#rangeForm`.
- `includes/classes/class.app.php` — `setRange()` stores `$_SESSION['range_offset']`;
  `resetRange()` clears it back to `0`.
- `includes/loader.php` — on every request, if `range_type == "manual"` and
  `range_offset` is set, recompute `range_end = now` and
  `range_start = now - range_offset seconds` (mirrors the existing "auto"
  recompute block immediately above it).

## Verified

- Confirmed on prod: picking "Last 30 Minutes" fresh after the deploy, waiting,
  then refreshing (or switching servers and back) now shows a current window
  instead of the old frozen one.
- Note: a range picked **before** this deploy stays frozen (its session never
  got a `range_offset`) until re-picked once — expected, not a residual bug.
